## 背景

task-15 要交付两件事：标定工具链（Part A）与 Phase 1 集成验证（Part B）。
落地时有六处需要决策，其中三处是任务书原文与仓库现状**直接冲突**。

**第一处：任务书说"标定输出 → ROS `camera_info`"，但给的实现接不上。**

原文用 `cv2.FileStorage` 写 YAML。2026-07-31 实测（OpenCV 5.0.0）：

```
%YAML 1.2
---
image_width: 640
camera_matrix: !!opencv-matrix
   rows: 3
   ...
```

`yaml.safe_load()` 读它抛 `ConstructorError: could not determine a constructor
for the tag 'tag:yaml.org,2002:opencv-matrix'`。而 ROS 的 `camera_info_manager`
走的正是普通 YAML 解析。也就是说，**那条接口是断的**，但断得很安静：
脚本跑完会打印"Results saved to: camera_intrinsics.yaml"，文件也确实生成了。

（OpenCV 4.x 写的首行是 `%YAML:1.0`，PyYAML 连扫描都过不去，报错更早。
本机装不上 4.x 的轮子——见 §影响，所以 4.x 那一条是从格式推断的，不是实测的。）

**第二处：IMU 标定的输出单位与驱动要的单位不是一回事。**

`config/real_sensors.yaml` 的 `icm42688` 段收的是 `gyro_noise_stddev` /
`accel_noise_stddev` —— **离散**采样的标准差。而 Allan 方差解出来的、
Kalibr 与 `robot_localization` 用的，是**连续时间噪声密度**（`rad/s/√Hz`）。
两者差一个 `√采样率`：100 Hz 下差 10 倍，协方差差 100 倍。

任务书 §优化建议 1 列出了六个输出字段，但没提这层换算。照着填的话，
滤波器会把 IMU 的噪声当成实际的百分之一，也就是把 IMU 当成基准真值。

**第三处：五个话题名在仓库里一个都不存在。**

原文的 `record-calib-bag.sh` 录的是 `/drone/rgb/image_raw`、
`/drone/rgb/camera_info`、`/drone/depth/image_raw`、`/drone/imu/data_raw`、
`/car/imu/data_raw`。仓库里实际是：

| 任务书 | 仓库实际 | 出处 |
|--------|---------|------|
| `/drone/rgb/image_raw` | `/drone/camera/rgb/image_raw` | `drone_edge.yaml` |
| `/drone/depth/image_raw` | `/drone/camera/depth/image_raw` | `drone_edge.yaml` |
| `/drone/imu/data_raw` | `/mavros/imu/data` | `drone_edge.yaml` |
| `/car/imu/data_raw` | `/car/imu/data` | `car_edge.yaml` / `real_sensors.yaml` |
| `/drone/rgb/camera_info` | **不存在** | —— |

`rosbag record` 订阅一个没有发布者的话题**不报错**，它就那么等着，
录出一个 0 条消息的 bag。相机标定要人举着标定板站两分钟，IMU 标定要静置两小时。
这一类错误的代价不是"再跑一遍脚本"，是"重来一次采集"。

（ADR-0009 §背景记的是同一类事：task-14 落地时抓到三处话题/类型不一致。）

其余三处：外参标定在 Phase 1 到底做到哪、样本数据从哪来、
焦距的"合理性"区间怎么定。

## 决策

### 决策 1：相机内参写 ROS `camera_info` 布局的普通 YAML，用 PyYAML

键名与 `camera_calibration` 包产出的一致：`image_width` / `image_height` /
`camera_name` / `camera_matrix` / `distortion_model` / `distortion_coefficients` /
`rectification_matrix` / `projection_matrix`。单目未校正相机的
`rectification_matrix` 取单位阵、`projection_matrix` 取 `[K|0]`。

代价是**放弃 `cv2.FileStorage` 的便利**（它能一行写一个矩阵），
换来的是三件事：

1. 标定结果能直接喂给 ROS，不需要中间转换脚本；
2. `validate-calibration.py` 只依赖 PyYAML —— 它必须能在没装 OpenCV 的
   树莓派上跑。一个"要先装 OpenCV 才能检查标定结果"的检查，现场没人会跑；
3. 结果文件能被 `git diff` 读、能贴进工单。

本项目自有的溯源信息（RMS、逐张误差、图片数、标定日期、序列号、
OpenCV 版本）放在 `air_ground_calibration:` 这个额外的顶层键下。

⚠ **`camera_info_manager` 是否忽略这个额外键，本机核实不了**（没有 ROS）。
按其实现应当是按键名读取、忽略未知键，但这是推断不是实测。
所以：`calibrate-camera.py` 带 `--strict-camera-info` 开关可生成不含该段的版本，
核实步骤写进 `src/deployment/calibration/README.md` §5 第 1 条，上机第一件事做。
这是 ADR-0010 §决策-3 的同一条规矩 —— 没核实的，自曝并给出核实步骤。

`test_calib_pipeline.py::test_04_opencv_filestorage_stays_incompatible` 把
"FileStorage 输出 PyYAML 读不了"这个**前提**锁住了。哪天它变绿，
该做的是回来重读本 ADR，而不是删掉那个断言。

### 决策 2：IMU 输出连续噪声密度，并附一段算好的驱动派生值

`imu_intrinsics.yaml` 的主字段是六个连续时间量（任务书 §优化建议 1 那六个），
外加一段：

```yaml
derived_for_driver:
  note: "填进 config/real_sensors.yaml 的 icm42688 段;
         sigma = noise_density × sqrt(sample_rate_hz)"
  gyro_noise_stddev: 2.020377e-03
  accel_noise_stddev: 1.482102e-02
```

为什么主字段是密度而不是标准差：密度与采样率无关，标准差不是。
把 ODR 从 100 Hz 改到 200 Hz，密度不变，标准差要乘 √2。存标准差的话，
改一次采样率就得重标一次 IMU —— 而那是两小时。

为什么还要附派生值：换算漏掉的后果太安静。`validate-calibration.py`
会验 `derived_for_driver` 与密度自洽（`test_11_driver_stddev_conversion`），
所以这两个数不会各自漂移。

字段名与 Kalibr 的 `imu.yaml` 一一对应（`gyroscope_noise_density` 等），
`convert-bag-to-kalibr.py` 是一层平凡映射 —— 这是设计目标，不是巧合。

### 决策 3：相机-IMU 外参，Phase 1 只交付接口、格式与采集检查

**交付**：输出 YAML 的字段与语义（含 `direction` 字段写明变换方向）、
bag 合规性检查（频率/时长，离线可查）、该跑的 Kalibr 命令。
**不交付**：解算。

两条理由，第二条更重要：

- Kalibr 是一整套 ROS + ceres + suitesparse，装不进本项目任何一个 CI job；
- 相机-IMU 外参**必须有真实的六自由度激励数据**才有意义。仿真里造不出来；
  合成数据造出来也只是把自己设的外参解回来 —— 那证明的是"矩阵乘法没写错"，
  不是"标定流程对"。

模板里的 `T_cam_imu` 是单位阵，`status: PLACEHOLDER`。
**单位阵是完全合法的 SE(3)**，正交性、行列式、基线长度全部通过 ——
只有 `status` 能区分"还没标定"和"外参恰好为零"。
`validate-calibration.py` 因此判失败，`test_22` 断言的正是这一条。

这与 ADR-0010 §决策-3 是同一个模式：**配置文件的存在本身不能成为
"功能已就绪"的假证据**。

### 决策 4：CI 的标定样本用**合成真值**，不用真实照片

`test/make_sample_calib_data.py` 按已知的 K 与畸变系数反向渲染 12 张棋盘格，
另生成一段已知零偏/噪声密度的静置 IMU 日志。CI 里现生成、现标定、现断言。

理由是**真实照片的真值是未知的**。拿一组照片标出 `fx=520`，没有任何办法
判断这个 520 对不对 —— 只能看 RMS，而 RMS 小只说明"这组解与这组观测自洽"。
一个把所有角点坐标同时缩放 1.1 倍的 bug 会让 `fx` 变成 572，**RMS 纹丝不动**。

合成数据能断言"解出来的 fx 与设进去的 fx 差多少"。2026-07-31 本地实测
（OpenCV 5.0.0 / numpy 2.5.1）：

| 量 | 真值 | 解出 | 偏差 | CI 容差 |
|------|------|------|------|--------|
| `fx` | 520.0 | 520.917 | +0.18% | 1% |
| `fy` | 519.0 | 519.856 | +0.16% | 1% |
| `cx` | 322.0 | 321.941 | −0.06 px | 3 px |
| `cy` | 238.0 | 237.939 | −0.06 px | 3 px |
| RMS | — | 0.137 px | — | < 0.30 px |
| `k1` | 0.12 | 0.1157 | 0.0043 | 0.05 |
| `k2` | −0.25 | −0.2113 | 0.0387 | 0.10 |
| `gyro_noise_density` | 2.0e−4 | 2.020e−4 | +1.0% | 10% |
| `accel_noise_density` | 1.5e−3 | 1.482e−3 | −1.2% | 10% |

容差取实测偏差的 3~10 倍，给 CI 上钉的 OpenCV 4.8~4.12 留版本间差异的余量。
再松就失去意义（`fx` 差 5% 的标定是废的），再紧会因为换个小版本而红。

**代价必须写明**：合成数据证明不了 OpenCV 的 `plumb_bob` 模型拟合得了真实镜头
——图就是按那个模型画出来的，属于自己考自己；也没有运动模糊、卷帘快门、
光照不均。那些只能靠上机采一次数据来验（README §5 第 2、3 条）。

顺带两个实测结论，都写进了脚本注释：

- 手算的 RMS 与 `cv2.calibrateCamera` 的返回值 **是同一个数**（比值 0.999997）。
  任务书原文把它们当成"重投影误差"和"RMS"两个指标分别打印，是重复计算。
- 任务书原文的 `cv2.norm(img_points[i], projected, cv2.NORM_L2)` 在
  OpenCV 5.0 上**直接抛异常**：4.x 的 `findChessboardCorners` 返回 `(N,1,2)`，
  5.0 返回 `(N,2)`，而 `projectPoints` 一直是 `(N,1,2)`。改成
  `reshape(-1, 2)` 后两个版本都对。

### 决策 5：焦距的合理性区间按**视场角**定义，不用 `0.5w < fx < 2.0w`

任务书给的区间换算过来是 HFOV ∈ (28.1°, 90.0°)：

```
fx = (w/2) / tan(HFOV/2)      fx = 2.0w → HFOV = 28.07°
                              fx = 0.5w → HFOV = 90.00°
```

**这个区间装不下本项目自己的硬件**。RealSense D435i 的深度流标称
87°±3° HFOV，对应 `fx ≈ 0.527w`；上沿 90° 正好压在 `fx = 0.5w` 的边界上。
一次完全正常的深度相机标定有可能被判成"焦距不合理"。
（彩色流 69.4° → `fx ≈ 0.722w`，余量充足；出问题的是深度流。）

改成 HFOV ∈ [20°, 120°]，即 `fx ∈ [0.2887w, 2.836w]`。再宽没有筛查意义，
再窄会误杀真实硬件。校验输出里直接打印反推的 HFOV —— "fx=520" 对人没有意义，
"HFOV=63°" 一眼能看出是不是手里那颗镜头。

同时把 `fy` 的判据从"对比图像**高度**"改成"对比 `fx`"：
`fy/fx ≈ 1` 是方形像素的直接表述，而 `fy` 与图像高度之间本来就没有关系
（16:9 与 4:3 的同一颗镜头 `fy` 相同、高度不同）。

### 决策 6：采集脚本的话题名由交叉引用测试守着，而不是靠人看

`record-calib-bag.sh` 里的话题名写死在脚本顶部的 `*_TOPIC` 变量里，
由 `validate_consistency.py::check_calibration_topics()` 断言它们
真的出现在 `car_edge.yaml` / `drone_edge.yaml` / `real_sensors.yaml` 里。
负向测试跑过：把 `/car/imu/data` 改回任务书的 `/car/imu/data_raw`，检查立刻红。

外加一道运行时防线：脚本在开录之前跑 `rostopic list` 逐个确认话题在线，
不在线就拒绝开录并说明原因。静态检查防"话题名抄错"，运行时检查防
"话题名对但节点没起来"—— 两种都会录出空 bag。

同 `validate.sh` §7「交叉引用」与 ADR-0003 黄金帧的用意：
**跨文件、跨语言、跨进程的契约，必须有一处会因为不一致而报警。**

## 被否决的方案

### 方案 B：沿用 `cv2.FileStorage`，另写一个 `filestorage_to_camera_info.py`

否决。多一个转换步骤就多一个会被忘掉的步骤，而忘掉的表现是
"ROS 加载不了标定结果"——排查时人会先怀疑 ROS 配置，不会怀疑文件格式。
直接写对的格式，成本是多二十行 `build_camera_info()`。

### 方案 C：IMU 只输出 `real_sensors.yaml` 要的离散标准差

否决。丢掉的是"这个数是在哪个采样率下测的"这一信息，
而 ODR 是会改的（`real_sensors.yaml` 里 `update_rate` 就是个可调参数）。
改一次 ODR 就要重标两小时，代价明显高于多存一个字段。

### 方案 D：提交 5 张真实棋盘格照片作为 `sample_calib_data/`

否决理由见决策 4：真值未知，断不出对错，只能断"RMS 小"，
而 RMS 小是几乎所有错误标定都满足的。

次要理由：本机没有相机，所谓"真实照片"只能从网上找，
那既不是本项目的镜头，也没有可信的方格尺寸 —— 一份来路不明的样本
比合成样本更糟，因为它看起来像真的。

### 方案 E：Phase 1 就把 Kalibr 集成进 CI（用官方 docker 镜像）

否决。CI 能跑起来不等于结果有意义 —— 没有真实激励数据，
跑出来的只有"合成外参能被解回来"。把一个每次运行十几分钟、
证明力为零的 job 挂进 CI，是在给未来的自己制造噪声。

### 方案 F：串口回路测试照任务书写成 shell heredoc 里的 Python

否决。`bash -n` 只检查 shell 语法，`py_compile` 看不见 heredoc 里的内容，
于是那段代码**不被任何门禁覆盖**—— 而它是 ADR-0003 帧协议的**第三份独立实现**
（另两份是 STM32 与 MSPM0 固件），恰恰是最该被测的那种代码。

拆成 `test-serial-loopback.py` 之后，它进了 `validate.sh` §2 的 py_compile
与自测，还能在没有硬件的机器上跑 13 条协议断言，其中黄金帧与固件的
`test_protocol.c::test_pong_golden_frame` 同源。
（同样的理由让 `validate_consistency.py` 早先从 `validate.sh` 的 heredoc 里搬了出来。）

### 方案 G：Observation 数据流验证照任务书写 `MockObservation` + 模拟预处理函数

否决，而且这是本次最值得记的一条。

原文写了一个二十行的 `preprocess_to_observation()`，注释是"模拟
`car_preprocessor.py` 的核心逻辑"。那三个用例**一定会通过**，因为它们测的是
那二十行模拟件。而真的 `CarPreprocessor.build_messages()` 里有五件模拟件
一件都没有的事：新鲜度窗口、LiDAR 降采样与 `angle_increment` 同步放大、
无效距离写 −1.0、超声波限幅与缺失填 `max_range`、`modalities` 由新鲜度生成。

这五条全是实机上真正会出问题的地方。举一个：雷达线松了，节点不报错，
若没有新鲜度窗口，`Observation` 里会一直带着几秒前的旧 `lidar_ranges`，
下游拿它当当前障碍物。

改成用 task-14 已有的 ROS 替身（`test/host/ros_stub.py`）跑**真的**
预处理器和**真的** `WorldModelStore`。为此给替身补了 15 个消息类
（`Image` / `Odometry` / `Observation` / `WorldState` …）与
`Subscriber` / `Timer` / `CvBridge`；`cv2` 用真的，所以 JPEG 压缩那一段是真跑的。
替身的字段忠实度由 `test_ros_stub_fidelity.py` 在 ROS 容器里拿真消息类比对。

补替身的过程当场抓到一个替身缺陷：`rospy.Duration(1.0 / publish_rate)` ——
`car_preprocessor.py` 的原话 —— 在替身上 `TypeError`，因为替身只收关键字参数
而真 `rospy.Duration` 收位置参数且接受浮点秒。
在此之前没有任何测试构造过 `Duration`。现在
`test_time_and_duration_behave_like_rospy` 拿真 rospy 逐项比对。

  `validate_consistency.py` 增标定话题交叉引用；`validate.sh` §2 挂两项自测
- **测试**：本地实测 —— 标定流水线 16/16、串口协议 13/13、
  Observation 数据流 10/10、task-14 既有 host 用例 69/69 无回归
- **CI**：`validate-deployment` job 增装 `numpy` + `opencv-python-headless`
  （`-c requirements.txt`）；新增 `smoke_test_phase1` job，含**反向验证**
  （删掉一个交付物后冒烟测试必须失败）
- **仓库**：`.gitignore` 增标定原始数据规则（按目录拦，不写裸 `*.bag`/`*.png` ——
  沿用 ADR-0010 §决策-4 对宽泛规则的顾虑）
- **本地环境的局限（必须写明）**：本机是 Windows + Python 3.14，
  `numpy<2.0.0` 没有 cp314 轮子，**装不上 CI 钉的版本**。
  所有标定数值是在 OpenCV 5.0.0 / numpy 2.5.1 上实测的，与 CI 钉的
  OpenCV 4.8~4.12 / numpy 1.x **不是同一套**。代码只用两个版本都稳定的 API，
  并显式做了 `reshape(-1, 2)` 的形状归一（决策 4 最后一条正是这个差异咬出来的）；
  但"CI 上跑出来的数与上表一致"这件事，第一次 CI 运行之前没有被验证过。
- **待决（承 ADR-0010，上机时必须处理）**：
  1. PX4 是否支持 MAVLink 签名、参数名 → `nsh> param show MAV_*`
  2. MAVROS 的签名参数入口 → `rosparam list | grep -i sign`
  3. `camera_info_manager` 是否接受 `air_ground_calibration` 额外段（本 ADR 决策 1）
  4. `/car/openmv/image_raw` 是否真有发布者 —— Phase 1 的 `openmv_bridge.py`
     只发 `detections`，车机相机标定可能采不到图（README §5 第 5 条）
- **流程**：以后往仓库里加"测试"，如果它测的是一份"模拟被测对象核心逻辑"的
  替代实现，必须在评审里被否掉。替身可以替**环境**（ROS、硬件、时钟），
  不能替**被测对象**。
