# ADR-0005: 边缘节点采用容器化部署

**状态**：已采纳

**日期**：2026-07-30

**决策者**：vista777-nk（项目负责人）、执行端 subagent（task-12 实现与验证）

---

## 背景

Phase 1 要把仿真里跑通的 ROS 节点搬到两台树莓派5 上（车机边缘 + 无人机边缘）。
这两台机器的共同点比看上去多：同一套 ROS 包、同一份接口定义、同样需要在
断网的场地上可靠开机自启；差别只在接了什么硬件、启动哪个 launch。

问题是**用什么形式把软件放上去**。

裸机部署（apt 装 ROS + catkin build + systemd 直接跑节点）是 ROS 社区的默认做法，
文档最多、调试最直接。容器化多一层抽象，也多一层出问题的地方。

真正让天平倾斜的不是"容器更现代"，而是三件具体的事：

1. **ROS Noetic 只支持 Ubuntu 20.04**，而树莓派5 的官方系统是
   Raspberry Pi OS Bookworm（Debian 12）。裸机装 Noetic 要么换系统
   （放弃 Pi5 的官方内核与 VideoCore 驱动支持），要么从源码编译整个 ROS。
2. **两台 Pi 必须跑完全相同的软件**。任何"这台机器上多装了个包"的差异，
   都会在联调时变成"为什么只有无人机侧不对"。
3. **Phase 2 要换硬件**（Jetson Orin / 香橙派）。裸机方案下这意味着
   把整个装机流程重做一遍。

---

## 决策

### 决策 1：边缘节点跑在容器里，宿主机只装 Docker

宿主机保持"干净的 Raspberry Pi OS + Docker"，不装 ROS。
ROS Noetic、项目节点、Python 依赖全部封在 `air-ground-edge` 镜像里。

**理由**：这一条同时解掉了上面三个问题 —— 发行版矛盾被镜像隔离、
两台机器跑的是同一个镜像 ID、换硬件只需要改 base image 与重新构建。

**代价**（都是实打实的，不粉饰）：

- **多一层设备直通配置。** 串口、I2C、USB 相机都要显式挂进容器，
  且宿主机的组 GID 与镜像内的未必一致（见 `.env.example` 的 `HOST_GID_*`）。
  裸机方案里这些是"装好就能用"。
- **镜像体积。** ROS base + MAVROS + 项目包，ARM64 镜像约 2GB。
  离线分发要走 U 盘，`docker save | gzip` 之后仍有几百 MB。
- **首次构建慢。** 在树莓派上就地构建约 30–60 分钟。
- **多一层排查。** 一个"节点没起来"现在可能是 systemd、docker、
  compose、entrypoint、roslaunch 五层里任何一层的问题。
  为此在 `entrypoint.sh` 里加了逐项自检 —— 但这是补救，不是消除。

**明确不接受的理由**：不是因为"容器是最佳实践"。
如果 ROS Noetic 有 Bookworm 的官方包，裸机方案会更简单，应当选裸机。

---

### 决策 2：一个镜像两个角色，用环境变量区分

不做 `air-ground-car` / `air-ground-drone` 两个镜像。
角色由 `AIR_GROUND_ROLE` 决定，`entrypoint.sh` 据此选 launch 文件，
compose override 文件负责各自的设备直通。

**理由**：两个镜像意味着两条构建流水线、两份依赖清单，
而它们 95% 的内容相同。差异集中在**设备与启动命令**这两处，
恰好是 compose override 最擅长表达的。

**代价**：镜像里带着另一个角色用不到的依赖（车机镜像里也有 MAVROS）。
体积上多几十 MB，可以接受。

**边界**：若 Phase 2 无人机侧要加 GPU 推理运行时（CUDA 层几个 GB），
这条决策要重新评估 —— 那时体积差异就不是几十 MB 了。

---

### 决策 3：不用 `privileged`，逐个挂设备；并承认 systemd 加固管不到容器

task-12 §12.2 原文同时写了 `privileged: true` 和一份 `devices:` 白名单。
这两者是矛盾的：`privileged` 已经把宿主机所有设备节点和全部 capability
给了容器，那份白名单一行都不起作用，**只是看起来像做了权限控制**。

本工程删掉 `privileged`，改为逐个挂载具体设备（评审建议 1）。

**代价**：

- 新增一个传感器就要改 compose，不能插上就用
- 设备不存在时容器直接启动失败（对下位机/飞控是想要的行为，
  对可插拔传感器不是 —— 因此拆出了 `docker-compose.car-sensors.yml`）
- RealSense 是个例外：librealsense 要通过 libusb 直接访问设备，
  只挂 `/dev/video*` 不够，必须 bind mount 整个 `/dev/bus/usb`。
  这一处的权限范围确实比逐个 devices 宽松，是 RealSense 强加的取舍，
  记录在 `docker-compose.drone.yml` 的注释里。

**同时必须说清楚的一件事**：systemd unit 里那串
`ProtectSystem` / `NoNewPrivileges` / `PrivateTmp` **保护的不是边缘节点**。

该单元唯一的工作是调用 docker CLI；真正的负载跑在 dockerd 创建的容器里，
不在这个单元的 cgroup 和 namespace 内。这些指令能约束的只是那个
几十毫秒的 CLI 包装进程。

保留它们是因为聊胜于无（万一 compose 本身被利用），但**不能让它们
造成"已经上了沙箱"的错觉**。真正的隔离边界在容器侧：
非 root 用户、无 privileged、设备白名单、`network_mode: host` 带来的
网络暴露面（这一条是为 ROS 1 的多播与动态端口付的代价，没有更好的选择）。

---

### 决策 4：容器生命周期由 systemd 独占

compose 里 `restart: "no"`，systemd `Restart=always`。

**理由**：两个重启控制器叠在一起会产生一种极难排查的现象 ——
容器崩了 docker 就地重启，systemd 完全看不到，于是 `systemctl status`
显示一切正常、`RestartCount` 永远是 0，而节点其实已经在后台反复重启。

统一由 systemd 拥有之后：journald 收全部日志、`RestartCount` 反映真实次数、
`StartLimitBurst` 能在配置错误时停止无意义的重启循环。

**代价**：容器重启会经过 systemd 一圈，比 docker 就地重启慢几秒。
边缘节点不是毫秒级切换的服务，这个代价无关紧要。

---

### 决策 5：Phase 1 离线分发镜像，不引入 registry

`docker save | gzip` → U 盘 → `docker load`（评审建议 3）。

**理由**：场地大概率没有外网。原任务文档在 systemd 单元里写了
`ExecStartPre=docker compose pull` —— 没有 registry 时这条必然失败，
而 `ExecStartPre` 失败会让整个单元启动失败。
症状是"实验室里能起、拉到场地就起不来"，且日志里只有一句 `manifest unknown`。

改为 `require-image.sh` 检查本地镜像，缺了就打印能照着敲的补救命令。

**代价**：更新镜像要人跑一趟。Phase 2 引入 Watchtower 时再改，
届时**必须**加上"飞行/实验期间不自动更新"的时间窗约束。

## 被否决的方案

### 方案 B：裸机部署（apt 装 ROS + systemd 直接跑节点）

要求宿主机是 Ubuntu 20.04。树莓派5 上跑 Ubuntu 20.04 意味着放弃官方内核
与外设驱动支持（Pi5 的 RP1 南桥在旧内核上支持不完整）。
从源码编译 ROS Noetic 到 Bookworm 上是另一条更长的路，且每台机器都要重来。
否决。

### 方案 C：两个镜像（car / drone 各一个）

见决策 2 的理由。95% 内容相同的两条流水线，差异恰好能被 compose override
表达。否决（Phase 2 引入 GPU 层时重新评估）。

### 方案 D：K3s / Kubernetes 编排

两个节点、固定角色、硬件直通为主 —— 这是 K8s 最不擅长的场景，
而它带来的运维复杂度（etcd、CNI、设备插件）远超收益。
Phase 3 若真的出现"多台异构机器动态调度"的需求再谈。否决。
