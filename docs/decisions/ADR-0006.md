# ADR-0006: 静态 IP 分配与时钟同步主从关系

**状态**：已采纳

**日期**：2026-07-30

**决策者**：vista777-nk（项目负责人）、执行端 subagent（task-12 实现与验证）

---

## 背景

三台机器（实验室服务器 + 车机 Pi + 无人机 Pi）需要在**没有基础设施的场地**上
互相找到对方，并且在时间戳上对齐。

这两件事看起来无关，其实是同一个问题的两面 —— 都是"谁是那个固定不变的参照点"。
把它们放在同一份 ADR 里，是因为选错任何一个的症状都是**数据明明在发、
对端就是看不到**，而排查时很容易只怀疑其中一个。

### 为什么不能靠 DHCP + 主机名

- 场地上常常只有一个便携路由器，DHCP 池的分配顺序不可预测
- ROS 1 的节点注册用的是 IP 而不是主机名；即使 mDNS 能解析，
  节点也会把自己拿到的那个 IP 硬编码进 XMLRPC URI
- `ROS_MASTER_URI` 必须在**服务启动前**就写死在 `.env` 里，
  拿不到一个稳定地址就没法开机自启

### 为什么时间对齐是硬需求

World Model 按时间戳做新鲜度过滤（task-07）。两台 Pi 差 200ms 的话，
无人机刚上报的观测会被判为"过期"而丢弃 —— 现象是数据在发、
服务器侧看不到，而且时好时坏（取决于两台机器时钟漂移的方向）。

树莓派**没有 RTC 电池**，每次上电时间都是错的。这不是"最好同步一下"，
是"不同步就不工作"。

## 决策

### 决策 1：`192.168.1.0/24` 固定分配

| 设备 | IP | 角色 |
|------|-----|------|
| 实验室服务器 | `192.168.1.100` | ROS Master + GPU 推理 + TCP :9090 |
| 车机树莓派 | `192.168.1.10` | Edge + MAVLink 汇集 + **NTP 服务器** |
| 无人机树莓派 | `192.168.1.20` | Edge + MAVROS |
| 路由器/网关 | `192.168.1.1` | — |
| 3DR 数传 | 不参与局域网 | 点对点串口透传 |

**分配规律**：末位 `10`/`20` 给移动单元（按角色留出扩展位：
再加一台车机就是 `.11`），`100` 起给固定设施。
`.1`–`.9` 留给网络设备，`.200+` 留给 DHCP 池（临时接入的调试笔记本）。

**理由**：`192.168.1.0/24` 是绝大多数便携路由器的默认网段，
换一个路由器不用重配所有设备。用 `10.x` 或 `172.16.x` 更"专业"，
但每次换场地都要先改路由器。

**代价**：与家用/办公网络冲突的概率高。若现场已有 `192.168.1.0/24`，
必须换一个独立路由器而不是接进现网 —— 反正 ROS 1 无认证的
多播流量本来也不该出现在别人的网络里。

---

### 决策 2：IPv6 关闭

`.nmconnection` 模板里 `[ipv6] method=disabled`。

**理由**：不是洁癖。ROS 1 只走 IPv4，但节点注册时若拿到 IPv6 地址，
会向 Master 注册一个别人连不上的 URI。症状是节点在 `rosnode list` 里可见、
话题却永远收不到数据 —— 与 `ROS_IP` 设错的表现一模一样，
排查时会互相干扰。

---

### 决策 3：`ROS_IP` 必须显式设置，不允许留空

`docker-compose.edge.yml` 里写的是 `ROS_IP: ${ROS_IP:?...}` ——
未设置时 compose **直接报错退出**，而不是用默认值。

**理由**：树莓派上同时存在以太网、WiFi、可能还有 4G。ROS 会自己挑一个
网卡地址注册到 Master，挑错的话就是上面那个"节点可见但没数据"的症状。

让它在启动时就响亮地失败，好过在联调时花两小时查一个静默的错配。

**代价**：`docker compose config` 在没有 `.env` 时也会失败 ——
包括 CI 的校验。因此 CI job 里显式注入了一组假值。这是刻意的：
如果 CI 能在没有 `ROS_IP` 的情况下通过，那这条约束就是假的。

---

### 决策 4：车机 Pi 作为局域网 NTP 服务器

无人机 Pi 与实验室服务器都向 `192.168.1.10` 同步（评审建议 2）。

**理由**（三条，按重要性排序）：

1. **车机是 MAVLink 的汇集点。** 空地链路是
   `无人机 Pi →(3DR air)→(3DR ground)→ 车机 Pi → 服务器`。
   时间基准放在数据流的汇聚处，跨机时间戳对齐的误差链最短。
2. **车机在地面，GPS/PPS 信号比飞行中的无人机稳定。** 接了 GPS 模块之后
   车机能提供 stratum 1 级别的参考。
3. **服务器可能不在现场。** 场地无外网时，让所有人依赖服务器反而更脆。

**关键配置**：车机侧写了 `local stratum 10 orphan`。
没有这一行的话，完全断网时 chrony 会拒绝对外服务，
另外两台机器各走各的表 —— 而新鲜度过滤只关心**相对差值**，
一个自洽但绝对时间可能错的基准完全够用。

**代价**：车机成了单点。它挂了之后另外两台会退回各自的公共 NTP
（客户端配置里留了备用 pool），但断网场地上就只能各走各的。
可接受：车机挂了的话，整个空地系统本来也停了。

## 被否决的方案

### 方案 B：DHCP 预留（MAC 绑定）+ mDNS

比静态 IP 优雅，但依赖路由器支持且配置在路由器上而不是在仓库里 ——
换个路由器就全丢了，而"配置必须可复现"是本项目的基本要求
（RESEARCH_PHILOSOPHY §一）。Phase 2 有固定实验室网络后可以重新评估。否决。

### 方案 C：实验室服务器当 NTP 服务器

直觉上服务器是"最中心"的节点。但它同时是最可能不在现场的那个 ——
外场实验时经常只有两台 Pi。见决策 4 的理由 3。否决。

### 方案 D：各机独立用公共 NTP，不做主从

断网时完全失效，而断网恰恰是外场的常态。否决。
