# ADR-0001: 采用项目规范与约定体系

**状态**：已采纳

**日期**：2026-07-25

**决策者**：ChatGPT（终审）、DeepSeek（起草）、vista777-nk（项目负责人）

---

## 背景

项目在规划阶段完成了四份核心文档（RESEARCH_PHILOSOPHY.md、PLATFORM.md、ICD.md、ROADMAP.md）和 9 个实施任务。但缺少关于仓库管理、命名规范、编码风格的统一约定。

ChatGPT 在终审中指出：

> "先不要急着跑 Gazebo。先 Repository。先 Workspace。先 Naming。先 Convention。以后我们会感谢今天的所作所为的。"

需要在仿真代码开始编写之前，建立一套可执行的基础设施规范。

---

## 决策

我们决定在本仓库中建立以下规范体系：

### 1. 仓库规范 (Repository)

- **分支策略**：简化 GitHub Flow（`main` + `feat/` / `fix/` / `docs/` / `exp/` 分支）
- **Commit 格式**：Conventional Commits 1.0.0，中文描述
- **Tag 策略**：语义化版本 + 论文快照 + 里程碑标签

### 2. 工作空间规范 (Workspace)

- **目录命名**：统一使用 kebab-case（例外：ROS package 用 snake_case）
- **仓库结构**：设计文档 / 任务 / ADR / 归档 分离
- **ROS 工作空间**：`~/air_ground_sim_ws/`，与仓库 `src/` 映射

### 3. 命名规范 (Naming)

- **文件**：核心文档 `UPPER_SNAKE_CASE.md`，任务 `kebab-case.md`，代码 `snake_case.py`
- **ROS package**：`air_ground_<功能>` 前缀
- **ROS Topic**：`/<robot_id>/<namespace>/<specific>` 层级
- **代码**：PEP 8，Type Hints

### 4. 编码规范 (Convention)

- **Python**：PEP 8，100 字符行宽，docstring 必须
- **注释语言**：变量/函数名用英文，模块/类 docstring 用中文
- **ROS**：参数 YAML 化，传感器断连不 crash，仿真 ≤ 30Hz
- **测试**：每个 task 有冒烟测试脚本
- **文档**：ADR 不可变，过时文档归档不删除

所有规范细节记录在 [CONVENTIONS.md](../../CONVENTIONS.md) 中。

---

## 备选方案

### 方案 B：不建立正式规范，靠代码审查自然形成

- **优点**：零开销，灵活
- **缺点**：半年后不可维护。新加入者（包括未来的自己）无法理解当初的约定。不符合 RESEARCH_PHILOSOPHY.md 中 "Laboratory Memory" 的核心定位。

**→ 否决。**

### 方案 C：采用 ROS 官方 REP 规范 + 英文 only

- **优点**：ROS 社区标准，国际化
- **缺点**：团队母语是中文，英文 docstring 增加认知负担，降低迭代速度。且 REP 规范不覆盖 Git 分支/Tag/仓库结构等层面。

**→ 否决。**

---

## 后果

### 正面

- 所有新代码和文档有明确的可遵循标准
- 合并审查时有检查清单可对照
- 未来任何人（包括 2028/2029/2030 的团队成员）阅读仓库时能快速理解约定
- 符合 RESEARCH_PHILOSOPHY.md 第一条："Platform First"——规范是平台的一部分

### 负面

- 初期有一定学习成本（需要读 CONVENTIONS.md）
- 需要在 code review 中持续执行，有维护成本
- 当前仓库中存在不符合新规范的目录名（`Project_Prometheus_Tasks/`、`Obsolete_or_Outdated_Documentation/`），已于 2026-07-27 重命名为 `project-prometheus-tasks/` 和 `obsolete-documentation/`

### 风险

- 规范可能过于严格，阻碍快速原型开发。缓解措施：`exp/` 实验分支不受完整规范约束，可以先跑通再规范化。
