# ADR-0012: cppcheck 从 ADVISORY 升为阻塞 —— 以及为什么它是唯一不钉版本的门禁

**状态**：已采纳

**日期**：2026-08-01

**决策者**：vista777-nk（项目负责人）、执行端 subagent（task-15 收尾）

**关联**：[ADR-0008](./ADR-0008.md) §决策-1「没实测过的不能设成门禁」——
本 ADR 是那条决策留下的**待办被兑现**，不是推翻它；
[ADR-0011](./ADR-0011.md) —— 同一轮任务的其余决策。

---

## 背景

task-13 建全仓 lint 门禁时，按「**是否在本地实测过**」把工具分成两层
（ADR-0008 §决策-1）。shellcheck / yamllint / flake8 三项提交前跑过全仓、
各 0 条，设为阻塞并钉死版本；cppcheck **一次都没跑过**（提交那台机器上
既没有 cppcheck 也没有 make），因此只设成 `continue-on-error: true`，
job 名带 `ADVISORY`，并在注释里写明：

> 首轮 CI 输出出来后再决定：若告警可控就升为阻塞并删掉这段注释；
> 若噪声大则调 `--suppress` 或撤掉。在那之前它只是一份报告。

到 task-15 收尾时，这个状态已经过了两夜。一个「每次 CI 都打印、
但没有任何人读、也不会让任何事失败」的步骤，本质上是 ADR-0008 想消灭的
那种东西的变体：它不是假绿灯，是**没有含义的灯**。

---

## 决策

### 决策 1：升为阻塞。依据是它的输出终于被观测到了

无法直接读 CI 日志（GitHub 的 job log 下载接口要求仓库 admin 权限，
本次执行环境没有 token），但**不需要读日志也能得到结论**：

该步骤的命令带 `--error-exitcode=1`，即 cppcheck 一旦在启用的
`warning,style,performance,portability` 四类严重度上有任何发现，
就返回 1。而 GitHub Actions 的 jobs API 会单独记录**每一步**的
`conclusion`，`continue-on-error` 只影响 job 的成败、不改写步骤自身的结论。

实测（2026-08-01 经公开 REST API 读取 `/actions/runs/{id}/jobs` 的 `steps` 数组）：

| CI run | commit | 任务 | cppcheck 步骤结论 |
|--------|--------|------|------------------|
| #24 | `9bab4b8` | task-14 | **success** |
| #25 | `fe0cf66` | task-15 | **success** |

两次退出码均为 0 ⇒ **两次都是零发现**。

零发现的检查设成阻塞没有代价：它今天不会拦住任何东西，而一旦将来有人往
`src/firmware/` 里写进一处 cppcheck 认得的问题，它会当场拦住。
这正是门禁应有的形态。

顺带修正一处会漂移的东西：job 注释里的文件计数（22/14 个）已经过期，
一并更新为 26 个 `*.sh` / 16 个 `*.y[a]ml` / 58 个 `*.py`。

### 决策 2：cppcheck **不钉版本号**，改用报错文案达成同一目的

ADR-0008 要求阻塞工具钉死版本，理由原文是：

> 不钉版本的话，上游加一条新规则就能把绿灯变红，
> 而看红灯的人无法区分"代码退化了"和"工具升级了"。

注意这条要求的**目的**是「让看红灯的人能区分两种红灯」，钉版本只是达成它的
一种手段。cppcheck 上这个手段的代价与另外三个工具不同：

| 工具 | 钉版本的做法 | 每次 CI 的代价 |
|------|-------------|---------------|
| shellcheck | 下载官方预编译二进制（1.6 MB） | 数秒 |
| yamllint / flake8 | `pip install x==版本` | 数秒 |
| **cppcheck** | **没有官方预编译 Linux 二进制**，只能源码构建 | **3~6 分钟**（加缓存后仍需维护缓存键） |

apt 里指定版本号也不可靠：GitHub 换 runner 镜像时那个版本会直接消失，
失败点从「lint 报错」搬到「装不上」，而后者同样是一次与代码无关的红灯。

所以这里改用另一种手段达成同一目的 —— 步骤运行前把版本号打出来，
失败时把两种可能直接写进报错：

```
::error::cppcheck 报了问题。两种可能, 先分清楚再动手:
  1) 固件 C 代码退化了 —— 按上面的行号改代码;
  2) <版本> 比上次跑的版本新, 多了一条规则 ——
     本步骤刻意不钉版本 (ADR-0012 §决策-2)。这种情况要么改代码
     迎合新规则, 要么加 --suppress 并在 ADR 里记一笔;
     **不要**把 --enable 调窄或把这一步改回 continue-on-error。
```

**代价写明**：判断从"自动"降级成"人读一行日志"。这比另外三个工具弱，
而且弱得可测量 —— 它多花的是一次人工判断，省下的是每次 CI 的 3~6 分钟。
选这一边，是因为固件 C 代码的改动频率远低于 CI 的运行频率。

最后一句「不要改回 continue-on-error」是刻意写进报错文案的：
一个被降级回告警态的门禁，就是本 ADR 一开始要解决的那个问题。

## 被否决的方案

### 方案 B：撤掉 cppcheck

否决。它刚刚证明了自己在本仓库上零噪声 —— 撤掉一个零成本且已经证明
干净的检查，是在丢掉信号。「有噪声所以撤掉」是合理的，
「没噪声所以撤掉」不是。

### 方案 C：继续留在 ADVISORY，等真正读到日志再说

否决，理由是这个状态本身就是问题。它已经过了两夜；而且这次拿到的证据
（两次步骤退出码 0）在强度上不比读日志弱 —— 日志能多告诉我们的只有
"零发现"以外的信息量，而零发现恰恰是这里唯一需要的结论。

### 方案 D：源码构建以钉死版本

否决，理由是代价与收益不成比例，见决策 2 的表。
如果将来 cppcheck 因为版本漂移红过两次以上，这个方案应当被重新考虑 ——
届时"人读一行"的成本就不再低于每次几分钟了。

### 方案 E：把 `--enable` 调窄（只留 `warning`）以降低将来的漂移风险

否决。当前 `warning,style,performance,portability` 四类零发现，
调窄不解决任何现存问题，只是**预先**放弃将来可能抓到的东西。
这类"为了不出错而少查"的调整，与 task-13 清掉的那两处
"永远不会失败的检查"是同一族。

## 影响

- **CI**：`lint-scripts` job 的 cppcheck 步骤去掉 `continue-on-error`，
  步骤名从 `ADVISORY` 改为 `blocking`；新增版本回显与失败诊断文案
- **门禁层级**：阻塞工具从 3 个变为 4 个。ADR-0008 §决策-1 的分层标准不变 ——
  cppcheck 是**通过了那条标准**才升上来的，不是被豁免
- **已知弱点**：cppcheck 是四个阻塞工具里唯一不钉版本的。上游加规则会造成
  一次与代码无关的红灯，需人工读一行版本号来判别（见决策 2 的代价说明）
- **本次未做**：本机的 cppcheck 仍未装上（Windows 版安装包 20 MB，
  实测下载速率约 10 KB/s，本轮未取到）。因此**没有本地实测数据**，
  升级依据完全来自 CI run #24/#25 的步骤退出码。若将来本地能跑，
  应补一次本地全量以确认结论
- **后续编号**：本 ADR 占用 0012。task-14 日记里提到的「超声波时序方案 A/B/C」
  仍待决，它将是 **ADR-0013** —— 与那篇日记原文的编号一致
