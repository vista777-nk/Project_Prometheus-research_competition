# ADR-0007: `network_mode: host` 的暴露面与 Phase 2 重估触发条件

**状态**：已采纳

**日期**：2026-07-31

**决策者**：vista777-nk（项目负责人，task-12 评审提出）、执行端 subagent（实现）

**关联**：[ADR-0005](./ADR-0005.md) §决策-3 决定了用 `network_mode: host`；
本 ADR 不推翻它，而是补上它没有写清楚的两件事——**暴露面到底有多大**，
以及**什么条件下必须重新评估**。ADR 不可变
（[RESEARCH_PHILOSOPHY](../../project-prometheus-tasks/RESEARCH_PHILOSOPHY.md) §ADR 规范），
故另立一份。

---

## 背景

task-12 评审指出：

> `network_mode: host` 下容器和宿主机共享网络命名空间——一个被攻破的 ROS 节点
> 可以直接访问宿主机的所有监听端口。Phase 2 如果有外网暴露的需求，这条要重新评估。

这个判断成立。ADR-0005 §决策-3 承认了这条代价，但只写了一句
"没有更好的选择"，留下两个缺口：

1. **暴露面没有量化。** "共享网络命名空间"具体意味着什么，
   在事故复盘时需要精确到"哪些东西本来是安全的、现在不是了"。
2. **没有重估的触发条件。** 一句"Phase 2 再说"在实践中的结果是永远不说——
   等到真的接外网时，这条约束已经沉在一份没人再读的文档里。

### 顺带修正 ADR-0005 的一处事实错误

ADR-0005 §决策-3 把理由写成 "ROS 1 的多播与动态端口"。
**ROS 1 不使用多播**——它的发现机制是中心化的：所有节点向 Master
（XML-RPC，固定 11311）注册，Master 把对端地址告诉它们，节点之间直连。
用多播做发现的是 ROS 2 的 DDS。

ADR 不可变，原文保留；真实理由见下文决策 1，以本文为准。

---

## 决策

### 决策 1：Phase 1 维持 `network_mode: host`，真实理由是端口不可枚举

ROS 1 的每个节点启动时会绑定**两个由内核分配的临时端口**：

- 一个 XML-RPC 端口（节点自己的 slave API，供 Master 和其他节点回调）
- 一个或多个 TCPROS 端口（每个发布中的话题一个监听套接字）

ROS 1 **没有**任何配置项能把这些端口限制到一个范围内
（`ROS_HOSTNAME` / `ROS_IP` 只影响注册的地址，不影响端口）。
一个车机边缘节点跑 5–8 个节点、十几个话题，端口集合每次启动都不同。

`bridge` 模式要求提前声明 `ports:`。声明不出来，就只能：

- 发布整个临时端口范围（`32768-60999`，Linux 默认）——那和 host 模式的
  暴露面几乎一样，却额外付出 NAT 转发的延迟和调试复杂度；或者
- 用 `--network=host` 之外的方案（见"被否决的方案"）。

**因此 Phase 1 维持 host 模式。** 这不是"暂时先这样"，
是在 ROS 1 + 单机部署这个约束下的正确解。

### 决策 2：把暴露面写成可核对的清单

`network_mode: host` 下，容器与宿主机共享同一个 network namespace。
具体后果，按"是否真的变差"分开列：

| 项 | host 模式下 | 备注 |
|----|------------|------|
| 容器进程能连宿主机 `127.0.0.1` 上的服务 | **能** | 这是真正新增的风险面。只绑 loopback 的服务（如某些管理接口）本以为不可达，实际可达 |
| 容器进程能绑定宿主机任意端口 | **能**（受 `NoNewPrivileges` + 非 root 限制，<1024 仍需 CAP_NET_BIND_SERVICE） | 容器内是非 root 用户，特权端口仍绑不了 |
| 宿主机的 iptables / nftables 规则 | **照常生效** | 网络策略仍然可控——这一点常被误以为"host 模式绕过防火墙"，并非如此 |
| 容器能改宿主机网络配置（路由、接口） | **不能** | 需要 `CAP_NET_ADMIN`，未授予 |
| 容器能嗅探宿主机全部流量 | **不能** | 需要 `CAP_NET_RAW`，未授予 |

结论：真正新增的是**第一行**——横向移动到宿主机 loopback 服务。
其余几项由 capability 而非 namespace 控制，host 模式并未放宽。

这张表的用途是：Phase 2 讨论时不必重新推演一遍，直接核对第一行还成不成立。

### 决策 3：三条重估触发条件，任一满足即**必须在动手前**重估

写成"动手前"而不是"尽快"，是因为这类事项一旦落后于实现就再也追不上。

| # | 触发条件 | 为什么是它 |
|---|---------|-----------|
| **T1** | 边缘节点所在网段接入外网，或 Pi 上出现任何监听 `0.0.0.0` 的非 ROS 服务（Web 控制台、Jupyter、远程调试端口） | 决策 2 表格第一行的风险从"内网横向"升级为"公网可达" |
| **T2** | 迁移到 ROS 2 | DDS 的发现走多播 + 可配置端口范围，`bridge` 变得可行，host 模式的理由消失 |
| **T3** | 同一台 Pi 上要跑第二个互不信任的工作负载（例如第三方视觉模型容器） | host 模式下它们共享 netns，互相之间没有任何网络隔离 |

**T2 尤其重要**：ROS 2 迁移时最容易发生的事，是把 compose 文件原样搬过去。
届时 host 模式会从"唯一可行"变成"没人想起来要改"。

### 决策 4：Phase 1 现在就做的补偿措施

不是"以后再说"，是这次就落地的：

1. **容器内非 root**（`Dockerfile.edge` 末尾 `USER airground`，uid 1000；
   compose 侧只用 `group_add` 补 dialout/i2c 两个宿主机 GID）——
   限制了绑定特权端口和读宿主机敏感文件的能力。
2. **宿主机上不跑绑定 `0.0.0.0` 的管理服务**。这是一条**部署纪律**，
   写进 `src/deployment/README.md` 的安全小节。SSH 是唯一例外，
   已由 `ssh/` 下的加固配置（禁口令、fail2ban）覆盖。
3. **静态 IP 在内网段**（见 [ADR-0006](./ADR-0006.md)），
   与外网之间隔着实验室路由器，不做端口转发。

这三条合起来把 T1 之前的实际风险压到"内网内、且需要先攻破一个 ROS 节点"。

## 被否决的方案

### 方案 B：`bridge` + 发布临时端口全范围

`ports: "32768-60999"`。暴露面与 host 模式相当（决策 1 已述），
却额外引入 NAT：`ROS_IP` 注册的是容器 IP，宿主机外的节点连不上，
必须再配 `ROS_IP=<宿主机IP>` 与端口一一对应——而端口是随机的，对不上。

**这个方案不只是代价高，是根本不工作。**

### 方案 C：macvlan，给容器独立的二层地址

技术上可行，容器拿到内网独立 IP，ROS 互通正常，且与宿主机 netns 隔离。

否决理由是**运维代价与 Phase 1 的规模不匹配**：
macvlan 下宿主机与容器默认互相不可达（同一物理口的 macvlan 子接口之间
内核不转发），要打通得再加一个 macvlan shim 接口；
WiFi 接口多数驱动不支持 macvlan（无人机上就是 WiFi）。
两台 Pi、单一工作负载的规模，不值得为此增加一层现场排查不了的复杂度。

**若 T3 触发，macvlan 是首选方案**——那时"互不信任的负载"这个前提
恰好让隔离的价值超过运维代价。

### 方案 D：现在就迁 ROS 2

超出 Phase 1 范围。Phase 0 的六个 ROS 包、仿真栈、MAVROS 全部是 ROS 1，
迁移是独立课题，不该由一条网络配置驱动。记为 T2。
