# ADR-0010: MAVLink 2 签名 —— 自测怎么写、什么时候启用、参数名核实不了怎么办

**状态**：已采纳

**日期**：2026-07-31

**决策者**：vista777-nk（项目负责人）、执行端 subagent（task-14 Part B 实现与验证）

**关联**：[ADR-0008](./ADR-0008.md) §决策-1「没实测过的不能设成门禁」——
本 ADR 把同一条标准用在**配置文件**上；
[SECURITY.md](../../SECURITY.md) §Phase 1 —— 实机阶段启用 MAVLink 签名。

## 背景

数传链路是这套系统里唯一离开机身、走无线电、且能下达控制指令的通道。
MAVLink 2 的消息签名要防三件事：链路劫持（注入伪造消息）、重放攻击、
未授权地面站接管。

task-14 §14B 给了四件交付物：密钥生成脚本、PX4 参数模板、MAVROS 配置、
签名自测脚本。落地时三件事需要决策。

**第一件：文档给的自测脚本跑不通，而且是"恒假"的那种跑不通。**

原文的核心断言是 `assert signed_len == unsigned_len + 13`，
但它两次 `pack()` 之间只设了 `mav.signing.secret_key`。实测（pymavlink 2.4.49）：

```
未签名 17 字节 → 设 secret_key 后 17 字节 → 断言 17 == 17 + 13 → False
```

pymavlink 里只设密钥**不会**签名，必须 `signing.sign_outgoing = True`。
另外原文用的 `mavutil.mavlink` 是 MAVLink **1** 的 v10 方言，拿它解签名帧
会报 `invalid MAVLink message length. Got 22 expected 9` —— 一条完全指错方向的报错。

**第二件：PX4 与 MAVROS 的签名参数名，在本地核实不了。**

原文给的是 `MAV_0_SIGNING=1` 和 `mavros/signing/{enabled,...}`。落地时：

- 原文引用的 `docs.px4.io/v1.14/en/advanced_config/mavlink_signing.html` 打不开；
- 检索到的官方 "MAVLink Message Signing" 页面只在 `main`（v1.18 时间线）路径下，
  v1.14 路径下没有对应页面；
- 本机没有 ROS，`rosparam list | grep sign` 跑不了。

也就是说：**这两个参数名一个都没被验证过**。

**第三件：什么时候启用。**

现在全系统跑在 SITL + localhost 上。

---

## 决策

### 决策 1：自测脚本按**黑盒行为**写五条断言，且显式用 v20 方言

不去断言 pymavlink 的内部字段，只断言外部可观测的行为。
2026-07-31 本地实测（pymavlink 2.4.49，Python 3.13）：

| # | 断言 | 实测 |
|---|------|------|
| 1 | 签名开销恰好 13 字节（link_id 1 + timestamp 6 + signature 6） | 21 → 34 ✓ |
| 2 | 同密钥可解出 HEARTBEAT | ✓ |
| 3 | 错误密钥被拒 | `MAVError: Invalid signature` ✓ |
| 4 | 同一帧重放被拒（时间戳未前进） | `MAVError: Invalid signature` ✓ |
| 5 | 未签名帧在期望签名时被拒 | `MAVError: Invalid signature` ✓ |

第 3–5 条是原文没有的。只测"签名后长度 +13"证明不了签名有用 ——
一个把 13 个零字节贴在帧尾的实现也能过。**要证明的是"错的进不来"，
不是"对的出得去"**。第 5 条尤其重要：它对应 `allow_unsigned: false`，
如果这一项失效，攻击者根本不需要密钥。

方言显式写 `pymavlink.dialects.v20.common`，不要 `mavutil.mavlink`
（后者按环境变量决定版本，默认 v1）。

自测挂在 `validate.sh` §2，本地与 CI 跑同一份；缺 pymavlink 时退出码 2 报 SKIP，
CI 的 `validate-deployment` job 装了 pymavlink（版本约束用
`-c requirements.txt` 引过来，不另抄一份），所以 CI 上一定真跑。

### 决策 2：Phase 1 **不在仿真里启用签名**，启用点定在实机首次地面联调

理由是取舍两边都算得出来：

- **现在开的收益 ≈ 0**：SITL + MAVROS + 通信桥全部绑 127.0.0.1，
  没有无线电，没有外部攻击面。
- **现在开的代价 > 0**：签名失败的表现是"链路建立正常、心跳正常、
  消息全部被丢弃"。这个症状在 Phase 0 的仿真调试里会与十几种别的原因混淆，
  而每一次误诊都要花掉排查时间。

启用点定在 task-15 实机首次地面联调，且**必须先做一次对照**：
关签名通一次 → 开签名再通一次。没有对照就上飞，等于把一个新引入的
"消息全丢"故障模式带到空中。

### 决策 3：参数名核实不了的，**不写进生效配置**，改交付"核实清单"

`px4-signing.params` 只保留能确定的传输参数（`MAV_0_CONFIG` / `MAV_0_MODE` /
`MAV_0_RATE` / `MAV_0_FORWARD`），签名段留空并写明为什么留空；
`mavros_signing.yaml` 整份标为"不被任何 launch 加载"的核实清单，
并给出上机后的四步核实流程。

这是 ADR-0008 §决策-1 从"CI 门禁"推广到"配置文件"。两者的失败方式一样：

- `param load` 遇到不存在的参数会**跳过并继续**，操作者得到一次"导入成功"，
  签名根本没开；
- `rosparam` 会老老实实把 `mavros/signing/*` 塞进参数服务器，
  MAVROS 从头到尾不读它，一切正常，签名没开。

两种情况下，**配置文件的存在本身成了"功能已启用"的假证据**。
这比没有配置文件更糟：没有的时候人还知道要去查。

代价写明：交付物里有两个 ⚠ 状态项，task-15 上机时必须处理，不能就这么过夜。

### 决策 4：密钥三道防线，且第一道是脚本本身不往仓库里写

1. `generate-mavlink-key.sh` 默认写到 `~/.config/air-ground/`，
   并显式拒绝往 Git 工作区写（`git rev-parse --show-toplevel` 判断）；
2. `.gitignore` 拦 `mavlink_secret.key` / `*_secret.key`；
3. `validate.sh` §5 扫 `src/deployment/` 下有没有 `*.key`。

第 1 道是新加的，也是最重要的一道 —— 沿用 `generate-ssh-keys.sh` 的做法：
「第一道防线是这个脚本本身从不往仓库目录写东西」。
task-14 原文的 `KEYFILE="mavlink_secret.key"` 写在当前目录，
在 `src/deployment/mavlink/` 里跑一次就会往仓库里落一个密钥。

`.gitignore` 里**刻意不写裸的 `*.key`**：仓库已经因为裸 `Makefile` 规则
吞掉过一个该入库的文件（见 .gitignore 内注释）。宽泛规则的失败是静默的。

密钥也绝不进 `.params` —— 那个文件是明文、会被导出、会被贴进工单。

## 被否决的方案

### 方案 B：照抄 `MAV_0_SIGNING=1` 与 `mavros/signing/*`

否决理由见决策 3。补一句量化：照抄的成本是 0，看起来交付更完整，
但它把"未核实"包装成"已配置"。等到实机那天，操作者会拿着一份导入成功的
参数表，以为签名开着 —— 而这正是签名要防的攻击面。

### 方案 C：现在就在 SITL 里把签名打开，"早开早发现问题"

否决理由见决策 2。这个论点在别处成立（比如早开 lint），
在这里不成立：签名的失败模式是静默丢包，它在仿真阶段制造的调试噪声
远大于它能提前发现的问题 —— 因为仿真阶段根本没有它要防的威胁。

### 方案 D：把密钥直接写进 `px4-signing.params` 里，省掉分发流程

否决。`.params` 会被 QGC 导出、会被贴进工单和聊天记录。
密钥必须走独立的安全通道，这是 SECURITY.md 已有的要求。

### 方案 E：把 MAVLink 签名自测挂进 `lint-scripts` job

否决理由是归属：它验的是**部署配置**，`validate.sh` 已经是部署配置的唯一入口，
本地与 CI 跑同一份。挂进 lint job 会让"部署校验"这件事出现第二个入口。
（Part A 的驱动测试挂 `lint-scripts` 是另一回事：那是 ROS 包的代码测试，
`validate.sh` 的范围只有 `src/deployment/`。）

## 影响

- **代码**：新增 `src/deployment/mavlink/`（生成脚本 / 参数模板 / 自测 / README）、
  `src/air_ground_drone_bringup/config/mavros_signing.yaml`
- **测试**：签名自测 **5/5 本地实测通过**，挂进 `validate.sh` §2
- **CI**：`validate-deployment` job 增装 `pymavlink`（`-c requirements.txt` 约束）；
  `validate.sh` §4 的 CRLF 检查范围加上 `*.params`；`.gitattributes` 加
  `*.params eol=lf`
- **安全**：`.gitignore` 增两条密钥规则；密钥默认路径移出仓库
- **待决（task-15 上机时必须处理）**：
  1. PX4 是否支持 MAVLink 签名、参数名是什么 → `nsh> param show MAV_*`
  2. MAVROS 的签名参数入口 → `rosparam list | grep -i sign`
  3. 两项核实完成后，把结论写成 ADR-0010 的后继 ADR（ADR 不可变）
- **流程**：以后往仓库里加"配置模板"，参数名没核实过就必须在文件顶部
  自曝，并给出核实步骤 —— 不能靠读的人自己去怀疑
