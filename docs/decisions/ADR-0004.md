# ADR-0004: TI 电赛合规主控选型与 MSPM0 移植层分离

**状态**：已采纳

**日期**：2026-07-29

**决策者**：vista777-nk（项目负责人）、执行端 subagent（task-11 实现与验证）

---

## 背景

Phase 1 的第二块下位机是差速底盘的 MSPM0G3507。它的存在有两个互相独立的理由，
必须分开说清楚，否则后续会有人把它当成"麦轮固件的简化版"而做出错误的取舍。

**理由一：竞赛规则约束。** 全国大学生电子设计竞赛（TI 杯）明确要求主控芯片为
TI 厂商产品，禁止使用 STM32 / Arduino / 树莓派等非 TI 主控承担核心控制任务。
这不是技术选型，是准入条件。

**理由二：架构验证。** 按 RESEARCH_PHILOSOPHY.md §五，真正稳定的是
**Capability（底盘运动控制）**，不是 Algorithm（具体哪颗 MCU）。
task-10 声称帧协议、PID、CRC 可以跨板复用 —— 这个声称在只有一块板的时候
是无法证伪的。task-11 是第一次真的把它拿去用。

同时 MSPM0G3507 与 STM32F407 在两个维度上差异显著，不能照搬：

| 维度 | STM32F407VET6 | MSPM0G3507 |
|------|---------------|------------|
| 内核 | Cortex-M4F，**硬浮点** | Cortex-M0+，**软浮点，且无硬件除法** |
| 主频 | 168MHz | 80MHz |
| Flash / SRAM | 512KB / 192KB | 128KB / 32KB |
| 官方外设库 | STM32Cube HAL（可选，寄存器映射公开可核对） | DriverLib + **SysConfig 代码生成** |

## 决策

### 决策 1：主控选用 MSPM0G3507，运动闭环全部在片内完成

树莓派 5 只做感知与通信中继，**不参与任何电机控制回路**。
编码器采样、逆运动学、PID、PWM 输出全部在 MSPM0 内部完成。

**理由**：这是竞赛准入条件，没有取舍空间。但同时也是好的架构 ——
把 1kHz 硬实时回路放在专用 MCU 上，Linux 上位机的调度抖动就永远影响不到它。

**代价**：MSPM0 的算力余量比 STM32 小得多（见决策 3 的量化）。
Phase 2 若要上电流环级联或模型预测控制，需要重新评估这颗芯片是否够用。

**合规边界**（写在这里避免日后争议）：树莓派可以发送 `(v, ω)` 指令、
读取遥测、做路径规划与感知；**不可以**直接输出 PWM、不可以读编码器、
不可以在上位机闭速度环。这条边界由协议本身保证 —— 协议里根本没有
"设置占空比"这条命令。

---

### 决策 2：差速逆解的饱和处理采用等比缩放，与麦轮固件一致

超出电机能力时，双轮同乘一个缩放系数，而非逐轮硬钳位。

**理由**：对差速底盘而言这不只是"方向更准"，而是一条可以精确证明的性质：

```
双轮同乘系数 s  ⟺  v' = s·v 且 ω' = s·ω  ⟹  曲率 κ = ω/v 严格不变
```

也就是说超速时车走的是**同一条弧线，只是慢了**。逐轮硬钳位会改变
`v_right / v_left` 的比值，直接把弧线掰弯 —— 上位机以为在走 R=0.5m 的圆，
实车走的是另一个半径，路径跟踪必然发散。

**代价**：达不到指令速度时车会整体变慢，而不是"尽力而为地保持速度"。
在需要抢时间的竞赛场景下，这可能不是想要的行为。
但"走错路径"的代价远高于"走慢一点"，且上位机可以通过读取
`FAULT_KINEMATICS_SAT (0x0010)` 知道自己发了做不到的指令，自行降速重规划。

**与文档的偏差**：task-11 §11.6 的 `test_saturation` 期望"双轮均钳位"。
直线饱和时两种策略结果完全相同，验不出区别；因此额外补了
`test_saturation_preserves_curvature`（v=1.0, ω=3.0，只有右轮超限），
它是唯一能区分两种策略的用例。

---

### 决策 3：不为 MSPM0 手写寄存器层，改为收窄的移植层 + 双构建剖面

固件里**唯一碰寄存器的地方**是 `common/mcu_port.h` 定义的约 15 个原语函数，
它有两份实现，编译期二选一：

| 剖面 | 移植层实现 | 可烧录 | 用途 |
|------|-----------|:---:|------|
| `ci-link`（默认） | `port_stub.c` | ❌ | CI 验证构建图与代码语义 |
| `driverlib` | `port_driverlib.c` | ✅ | 真实硬件，需 TI MSPM0 SDK |

**理由**：TI 官方支持的路径是 DriverLib + SysConfig 生成引脚配置，
而 MSPM0 SDK 无法在 GitHub Actions 上免登录安装。面对这个约束有两条路：

- **(a)** 手写一套 MSPM0 寄存器地址。能编过、CI 会绿、看起来很完整 ——
  然后在某个人真的烧录时，以最难排查的方式失败（外设静默不工作、
  中断进错向量）。task-10 敢手写 STM32F4 寄存器层，是因为那份映射
  公开且能逐条核对；MSPM0 的引脚复用 + 时钟分频 + 中断优先级三者
  由 SysConfig 联动生成，手写其中任何一处出错都难以定位。
- **(b)** 承认这个边界，把不确定的部分收拢到一个文件里，默认给空实现，
  并在每一处（`mspm0_conf.h` / README §2 / 构建横幅 / `.bin` 文件名 /
  `make flash` 拒绝执行）标明这不是可烧录固件。

**选 (b)。** 代价是"`make` 出来的 `.bin` 不能直接用"，
收益是没有人会因为一份看起来很完整的固件而浪费一整天。

**这个决策同时带来一个当初没预料到的收益**：移植层分离之后，
`encoder.c` 的回绕处理、测速窗口、EMA 滤波变成了纯逻辑，
可以在 Host 上用假编码器直接测（11 个用例）。

**这条经验随后回溯应用到了 task-10**（2026-07-29）：移植层接口提升为
`common/mcu_port.h` 两块板共用，麦轮固件新建 `port_stm32f407.c` 收拢全部寄存器访问，
`bsp.c/.h` 删除，Host 用例从 52 增至 63。发送策略的差异（STM32 用 TXE 中断、
MSPM0 就地忙等 FIFO）通过 `port_uart_tx_start()` / `port_uart_tx_next()` 的
回调反转挡在移植层里，两块板因此共用同一份 `uart.c` 环形缓冲逻辑。

之所以能低成本回溯：两块板都还没上板，不存在"已经能跑的不敢动"。
**结构性缺陷要在硬件到货之前修完。**

**代价（量化）**：每个控制周期多约 10 次函数调用，@80MHz 约 0.5µs，
相对 1000µs 的控制周期占 0.05%。可忽略。

**空实现剖面刻意保留的两个真实行为**：
- SysTick（ARM 内核外设，与 TI 无关）是真配的，1kHz 控制中断真的在跑，
  因此可以用调试器验证时序与栈占用，而不只是"能编过"。
- `port_encoder_read_count()` 恒返回 0 ⟹ 一给速度指令就会触发
  `FAULT_STALL`。这是**故意**的：把"移植层没接"变成一个上位机看得见的故障，
  而不是让车安静地不动。

---

### 决策 4：软浮点开销由预计算倒数消化，不改共享的 `common/pid.c`

Cortex-M0+ 既无 FPU 也无硬件除法指令，浮点全是 `__aeabi_*` 库调用。
`kinematics.c` 预先算好 `1/R` 与 `track/2`，`encoder.c` 的换算系数是编译期常量，
热路径上只做乘法。

估算（数量级，非实测）：1kHz 控制中断约 2000–3000 周期 @80MHz ≈ 25–38µs，
占控制周期的 **3–4%**。

**已知未优化项**：`common/pid.c` 的微分项写作 `(error - prev) / dt`，
每周期两次浮点除法（~300 周期）。改传 `1/dt` 可省掉，但要动与麦轮固件共享的代码。
3–4% 的占用不值得为此引入跨固件的 API 变更，记为 Phase 2 候选优化。

**代价**：如果 Phase 2 在同一个中断里再加电流环，这 3–4% 的基数会翻倍，
届时必须重新测算而不是沿用本估算。

## 被否决的方案

### 方案 B：用 STM32 跑差速底盘，MSPM0 只做"合规装饰"

把实际控制放在 STM32 上，MSPM0 只转发指令。**直接违反竞赛规则**，
且会让代码库里出现一颗谁也不敢删的假芯片。否决。

### 方案 C：把差速运动学并进麦轮的 `kinematics.c`，用 `#ifdef` 区分

两种底盘自由度不同（麦轮 3 DoF 可横移，差速 2 DoF 不可），
强行合并会产出一个到处是条件编译的四不像，且两块板的测试互相污染。
帧协议、PID、CRC 共享是对的，**运动学不共享也是对的** —— 共享的边界应该
落在"数学上确实相同"的地方，而不是"文件名看起来一样"的地方。否决。

### 方案 D：CI 里下载 TI MSPM0 SDK 完成真实构建

SDK 需要接受许可协议后下载，无稳定免登录直链；把安装包塞进仓库
会引入体积与许可问题。折中方案（决策 3）保留了 `PROFILE=driverlib`
入口，本地装了 SDK 的人可以随时构建真实固件。
若日后 TI 提供可脚本化的分发渠道，应当回来重新评估此项。否决（暂时）。
