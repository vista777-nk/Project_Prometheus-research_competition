# ADR-0008: CI 门禁分层 —— 哪些检查阻塞、哪些仅告警

**状态**：已采纳

**日期**：2026-07-31

**决策者**：vista777-nk（项目负责人）、执行端 subagent（task-13 实现与验证）

**关联**：[ADR-0004](./ADR-0004.md) §决策-3 决定了 MSPM0 移植层空实现，
本 ADR 解释这类"能构建但产物不可用"的 job 在 CI 里必须怎么自曝；
延续 [RESEARCH_PHILOSOPHY](../../project-prometheus-tasks/RESEARCH_PHILOSOPHY.md) §四「验证先行」。

---

## 背景

task-13 要把 CI 从"编译 + 测试"扩成多维度流水线。但真正做的时候发现，
五个维度里有四个（ROS / STM32 / MSPM0 / Docker）已经被 task-10/11/12
在交付各自功能时顺带建好了，只剩全仓静态检查这一维。

于是本任务真正需要决定的不是"要不要加 job"，而是一个更麻烦的问题：
**一个检查加进 CI 之后，它失败时该不该拦住提交？**

这个问题有代价，因为两个方向都会坏事：

- 全设成阻塞，会把没实测过的工具的第一轮输出直接变成红灯。
  代码没问题、工具在报噪声，但看红灯的人得先花时间证明这一点。
- 全设成非阻塞，就会得到本仓库当时已经有的那个东西 ——
  `validate-deployment` 里那个 `shellcheck --severity=warning ... || true`
  的步骤。它扫的范围窄（只有 `src/deployment`），末尾还 `|| true` 兜底，
  **无论仓库里的脚本烂成什么样它都是绿的**。

第二种更危险。一条永远不会失败的检查在 CI 面板上和一条真门禁长得一模一样，
它把"没查出问题"和"没查"这两件事混成了同一个绿勾。

同类问题在本仓库已经出现过第三次：README 顶部曾经挂着一个硬编码的
`img.shields.io/badge/CI-passing-brightgreen` —— 一个与构建结果完全无关、
永远显示 passing 的 badge。前两次是 task-12 的 CRLF 检查用 `grep $'\r'`
（MSYS 会静默剥掉 CR，本地永远绿）和 mspm0 的 `ci-link` 剖面。

**这些都不是同一个 bug，但是同一类失败：声称已验证，实际没验证。**

---

## 决策

### 决策 1：门禁强度按"**是否在本地实测过**"分层，不按工具的严格程度

一个检查设成阻塞的前提是：**提交它的人已经在本地拿真工具跑过全仓，并知道结果是几条**。
没跑过就只能是 `continue-on-error`，且必须在 job 注释里写明"没跑过"。

task-13 落地时的实测结果与对应处置：

| 工具 | 版本 | 范围 | 提交前实测 | 门禁 |
|------|------|------|:---:|:---:|
| shellcheck | 0.10.0 | 22 个 `*.sh` | error 0 条 / warning **4 条** | **阻塞**（修完 4 条后） |
| yamllint | 1.38.0 | 14 个 `*.yaml/*.yml` | **0 条** | **阻塞** |
| flake8 | 7.1.1 | 31 个 `*.py` | **0 条** | **阻塞** |
| cppcheck | 发行版版本 | `src/firmware/` | **未跑过**（本机无 cppcheck、无 make） | 仅告警 |

shellcheck 的门禁定在 `--severity=warning` 而不是 `error`：
实测 error 级本来就是 0 条，只卡 error 等于什么回归都拦不住 ——
新脚本引入 SC2164（`cd` 未判错）这类问题时 CI 照样全绿。
info/style 级 37 条不纳入，多是风格偏好，拿来拦提交性价比不高。

为了让这条门禁真的能设成阻塞，本任务修掉了那 4 条 warning，其中
`validate.sh` 的 SC2164 是真缺陷：`cd "${REPO_ROOT}"` 失败后脚本会继续跑，
在错误的目录里查出一份"全过"的报告。**校验脚本自己产生假绿灯**，
恰好是本 ADR 要防的那件事。

**cppcheck 的处理是这条决策的负面样例，特此写明**：它被加进了流水线，
但它的输出一次都没被人看过。设成阻塞就是拿别人的 CI 当试验场。
首轮 CI 输出出来后再定去留，在那之前它只是一份报告，不是门禁。

### 决策 2：门禁工具全部钉死版本号

三个阻塞工具全部锁版本：shellcheck 从 GitHub release 下载 `v0.10.0`
（**不用 apt** —— ubuntu-latest 的 apt 版本是 0.9.0，与实测用的不是同一版），
yamllint / flake8 用 `pip install "yamllint==1.38.0" "flake8==7.1.1"`。

代价是明确的：工具升级要靠人手动改这个数字，不会自动拿到上游的新规则。

换来的是一条更重要的性质：**红灯一定意味着代码有问题**。
不钉版本的话，上游加一条新规则就能把绿灯变红，而看红灯的人无法区分
"代码退化了"和"工具升级了" —— 区分这两件事的成本，比手动升版本高得多。

同时这也是决策 1 能成立的前提：如果 CI 跑的版本和本地实测的版本不是同一个，
"实测过"这个前提就是假的，分层标准本身也就失效了。

### 决策 3：一个检查只实现一处

新增 `lint-scripts` 后，同时删掉两处重复：

- `validate-deployment` 里那个非阻塞 shellcheck 步骤（范围被全仓扫描完全覆盖）；
- **不实现** task-13 §13.2 文档里写的 `systemd Unit Syntax Check` 步骤 ——
  `systemd-analyze verify` 已经由 `validate.sh` §6b 在 `validate-deployment` 里真跑了。

这是 task-12 既有做法的延伸：本地与 CI 跑**同一份** `validate.sh`，
因为两份必然漂移。同一个检查写两遍不增加信息，只增加两处要同步维护的逻辑，
以及一个"改了 A 忘了 B"的漂移点。

### 决策 4：绿灯 ≠ 产物可用，这一点必须由 job 自曝

CI 全绿只说明"构建和检查通过了"，不说明产物能上板、能上机。本仓库有两处是这样：

- `build-mspm0-firmware` 构建的是 `PROFILE=ci-link` 剖面，移植层为空实现，
  产出的 `.bin` **不可烧录**（ADR-0004 §决策-3）；
- `build-edge-image` 用 `outputs: type=cacheonly`，镜像根本没落盘，只验证"能构建"。

处置是**在产物名和 job 注释里自曝**，不指望读的人去翻 ADR：
mspm0 的 artifact 名字叫 `mspm0-diff-firmware-ci-link`，任何拿到它的人
一眼能看出这不是可烧录固件。

对应地，README 顶部的假 CI badge 换成 GitHub Actions 的真 badge。
一个永远绿的 badge 比没有 badge 更糟，理由和上面那条 `|| true` 完全一样。

## 被否决的方案

### 方案 B：自建 Jenkins / GitLab CI

task-13 原文要求为"GitHub Actions vs Jenkins"单独写一份 ADR。实际比下来，
这个决策**没有真实的取舍代价**，不值得单独成篇：代码已经在 GitHub 上，
公开仓库的 Actions 额度免费且无上限，而自建方案要先有一台常开的机器、
一套自己维护的 runner 和一份备份策略 —— 在一台树莓派都还没部署完的阶段，
这是纯增支出、零收益。

**真正值得记录的取舍是门禁强度**，也就是本 ADR 的正文。
把一个没有取舍的选择写成 ADR，会稀释 ADR 目录的信噪比。

自建方案唯一有实际价值的场景是 Phase 2 的自托管 ARM64 runner
（树莓派原生构建，省掉 `build-edge-image` 里 QEMU 模拟的数倍耗时）。
那是性能问题，等 `build-edge-image` 真的成为瓶颈时再单独决策。

### 方案 C：为 `src/firmware/common/` 单开一份 ADR

task-13 原文的第二份 ADR 要求。否决理由是**重复记账**：
`common/` 的设计决策已经由 ADR-0004 §移植层分离 和
`src/firmware/README.md` 记录，且 task-11 一行未改地复用了它 ——
这个设计已经被实践验证过，不需要一份事后追认的 ADR。

（另：task-13 原文把这两份 ADR 编号为 0007/0008，但 0007 已被 task-12 占用。
ADR 编号不可复用，见 RESEARCH_PHILOSOPHY §ADR 铁律。）

### 方案 D：给固件加 `-Werror`，把编译告警也变成门禁

技术上正确，且两个 Makefile 已经开了 `-Wall -Wextra -Wshadow -Wundef -Wdouble-promotion`。
否决理由是**本地无法验证**：提交时本机没有 `make`，也没有 arm-none-eabi 工具链，
无法确认加上之后两个固件还能不能编过。

按决策 1 的标准，这属于"没实测过"，那就不该设成阻塞 ——
而 `-Werror` 没有非阻塞形态。留到能实测时再定。

### 方案 E：用 `paths` 过滤器只在相关文件变更时跑对应 job

task-13 §13.3 自己就建议 Phase 1 先不加，本 ADR 沿用。
当前 CI 分钟数无压力，而 `paths` 会带来"改了 README 结果 CI 没跑"的混淆 ——
在一个正在建立"CI 说了算"这个习惯的阶段，这种混淆的代价高于省下的分钟数。

## 影响

- **CI**：新增 `lint-scripts` job（4 步：shellcheck / yamllint / flake8 阻塞，
  cppcheck 告警）；`validate-deployment` 减少一个步骤和一个 apt 包
- **代码**：修掉 4 条 shellcheck warning，其中 `validate.sh:29` 的 SC2164 是真缺陷
- **文档**：README 的假 CI badge 换成真 badge；Phase 1 计数 0/6 → 4/6
- **流程**：以后往 CI 加检查，先在本地跑一遍全仓并把条数写进 PR 描述；
  跑不了就设 `continue-on-error` 并在 job 注释里写明跑不了的原因
- **待决**：cppcheck 首轮 CI 输出出来后，决定升为阻塞还是撤掉；
  决定之前它在 job 名里带 `ADVISORY` 前缀
- **对后来者**：看到一条非阻塞检查时，能直接从 job 注释知道它是"暂时没实测"
  还是"故意只做参考"，不必猜
