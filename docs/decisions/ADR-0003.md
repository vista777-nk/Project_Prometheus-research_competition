# ADR-0003: 串口二进制帧协议统一设计

**状态**：已采纳

**日期**：2026-07-28

**决策者**：vista777-nk（项目负责人）、执行端 subagent（task-10 实现与验证）

---

## 背景

Phase 1 要把仿真里跑通的运动控制搬到实车上。实车的 Layer 1 有两块互不相同的下位机：

| 底盘 | 主控 | 内核 | 场景 |
|------|------|------|------|
| 麦轮 | STM32F407VET6 | Cortex-M4F，硬浮点 | 通用研究平台（task-10） |
| 差速 | MSPM0G3507 | Cortex-M0+，软浮点 | TI 电赛合规（task-11） |

两块板都通过 UART 挂在同一台树莓派 5 上，都要接收速度指令、都要回传轮速与故障。

如果让两块板各自定义一套串口协议，后果是可预见的：树莓派端要维护两个解析器，
两边的 CRC 实现会慢慢漂移，联调时"到底是谁的锅"要靠示波器判断。
更麻烦的是 Phase 2 换 MCU 时，上位机代码要跟着改——而按
RESEARCH_PHILOSOPHY.md §五，真正应该稳定的是 **Capability（底盘运动控制）**，
不是 Algorithm（具体哪颗 MCU）。

因此需要在写第一行固件代码之前，先把线上格式钉死。

---

## 决策

**采用统一的二进制帧结构，两块下位机共用同一套帧层与 CRC，只在命令集上有差异。**

### 决策 1：帧结构

```
┌────────┬────────┬──────────┬──────────────┬──────────┬────────┐
│  SOF   │  LEN   │   CMD    │    DATA      │  CRC16   │  EOF   │
│ 1 byte │ 1 byte │  1 byte  │ 0~251 bytes  │ 2 bytes  │ 1 byte │
│  0xA5  │  n+4   │          │              │ LSB→MSB  │  0x5A  │
└────────┴────────┴──────────┴──────────────┴──────────┴────────┘

LEN = CMD(1) + DATA(n) + CRC(2) + EOF(1) = n + 4,  LEN ∈ [4, 255]
CRC 覆盖范围 = CMD + DATA。SOF / LEN / CRC / EOF 本身不参与计算。
```

**为什么 LEN 包含 CRC 与 EOF**：这样接收方读到 LEN 后就知道"还要再收 LEN 个字节"，
状态机只需一个计数器，不必再做加减。代价是 LEN 的语义不那么直观，
所以在三份实现里都必须写清楚——这也是本 ADR 存在的理由之一。

### 决策 2：字节序统一小端

帧内所有多字节标量（float32、uint16）一律小端。Cortex-M4、Cortex-M0+、
树莓派 ARM64 三者原生都是小端，选小端等于三边都不用做字节交换。

浮点数按 IEEE-754 binary32 原样传输。Python 端对应 `struct.pack('<fff', vx, vy, omega)`。

### 决策 3：不做字节填充（byte stuffing）

载荷里出现 0xA5 或 0x5A 时**不转义**。

理由：LEN 字段已经界定了帧边界，接收方不需要靠"找 EOF"来断帧；
CRC16 + EOF 双重校验足以拒绝错位帧。引入转义反而会让帧长变得不可预测
（最坏情况翻倍），也让 LEN 字段失去意义。

**已知代价**：这是一个有意接受的权衡，不是疏漏。若线路噪声在一帧之前插入
一个杂散 0xA5，紧随其后的真实 SOF（0xA5 = 165）会被当成 LEN 字段，
解析器随即空等 165 字节（@115200 约 14ms）才会因 CRC/EOF 不符而重同步，
期间到达的正常帧全部被吞掉。

**缓解措施**：物理层检测到接收线路空闲时调用 `frame_parser_reset()`，
丢弃半截帧、回到等待 SOF 状态。上位机总是把一帧连续发完，因此
"收了半截 + 线路空闲"必然意味着已经失同步。STM32 侧由 USART IDLE 中断触发
（`uart.c` → `protocol_notify_line_idle()`）。该行为由
`test_parser_desyncs_on_stray_sof_and_idle_reset_recovers` 用例锁定。

### 决策 4：CRC-16/CCITT-FALSE

```
多项式 : 0x1021  (x^16 + x^12 + x^5 + 1)
初始值 : 0xFFFF
输入反射: 否   输出反射: 否   输出异或: 0x0000
测试向量: crc16("123456789") == 0x29B1
```

三方实现必须通过同一批测试向量。参考实现（C 版在 `src/firmware/common/crc16.c`）：

```python
def crc16_ccitt(data: bytes) -> int:
    """CRC-16/CCITT-FALSE —— 与固件 crc16.c 逐位等价。"""
    crc = 0xFFFF
    for byte in data:
        crc ^= byte << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) & 0xFFFF if crc & 0x8000 else (crc << 1) & 0xFFFF
    return crc

assert crc16_ccitt(b"123456789") == 0x29B1
```

选 CCITT-FALSE 而不是 MODBUS/ARC 之类：它是嵌入式串口场景最常见的参数组合，
在线校验工具（crccalc.com）默认就能对，联调时少一个扯皮点。

### 决策 5：命令集分板定义，公共部分保持一致

| CMD | 方向 | 名称 | STM32 麦轮 DATA | MSPM0 差速 DATA |
|-----|------|------|-----------------|-----------------|
| `0x01` | Pi→MCU | SET_VELOCITY | vx,vy,ω = 12 B | v,ω = 8 B |
| `0x02` | Pi→MCU | EMERGENCY_STOP | 0 B | 0 B |
| `0x03` | Pi→MCU | PING | 0 B | 0 B |
| `0x10` | Pi→MCU | （预留：电赛扩展外设） | — | 自定义 |
| `0x11` | MCU→Pi | TELEMETRY | 4×RPM + 4×电流 + 故障码 = 34 B | 2×RPM + 2×电流 + 故障码 = 18 B |
| `0x12` | MCU→Pi | ACK | 被确认的 CMD = 1 B | 同左 |
| `0x13` | MCU→Pi | PONG | major,minor,patch,board,chassis = 5 B | 同左 |
| `0xFF` | MCU→Pi | ERROR | 错误码 + 变长详情 | 同左 |

**板卡与底盘自述**：PONG 的后两字节是身份声明。

| 字段 | 取值 |
|------|------|
| `board_type` | `0x01` = STM32F407 · `0x02` = MSPM0G3507 |
| `chassis_type` | `0x01` = 麦轮 (mecanum) · `0x02` = 差速 (differential) |

树莓派启动时先发 PING，把 PONG 里的这两字节与 `CHASSIS` 环境变量比对，
不一致就拒绝启动。这道检查专治"接错串口 / 换了底盘忘改配置"——
用麦轮的解算去驱动差速底盘，车会原地打转撞墙，而且现象很难一眼看出原因。

### 决策 6：遥测主动上报，不轮询

下位机每 50ms（20Hz）主动发一帧 TELEMETRY。树莓派不需要请求。

理由：轮询会让每次读数都多一个 RTT，且上位机繁忙时遥测频率会跟着抖。
主动上报让下位机的行为完全可预测，也让"多久没收到遥测 = 下位机挂了"
成为一个天然的健康检查。

## 备选方案

### 方案 B：直接用 MAVLink（已拒绝）

- **优点**：现成的、经过实战检验的协议，工具链齐全（QGroundControl 可直接观察）
- **缺点**：最小帧头就 12 字节，对一条只传 12 字节速度指令的链路是纯浪费；
  MSPM0G3507 只有 32KB SRAM，塞进 MAVLink 解析器后留给控制逻辑的余量很紧张；
  且 MAVLink 的消息定义体系（XML → 代码生成）对两条命令来说过重
- 空地通信桥（Layer 2，task-06）已经在用 MAVLink 与飞控通信——
  那里用是对的，因为对端是 PX4。这里对端是我们自己的固件，没有兼容性负担

**→ 否决。**

### 方案 C：文本协议（形如 `V 0.5 0.0 1.0\n`）（已拒绝）

- **优点**：串口助手直接可读，调试门槛最低
- **缺点**：浮点解析在 Cortex-M0+ 上要拖进 `sscanf`，代码体积和耗时都不可接受；
  文本没有可靠的定界与校验，噪声很容易被解析成一个合法但错误的速度指令——
  对一台会自己跑的车来说，这是安全问题而不是可用性问题

**→ 否决。** 可读性的需求由上位机的解析脚本满足（task-15 提供），不必牺牲线上格式。

### 方案 D：两块板各定义各的协议（已拒绝）

- **优点**：各自实现最省事，互不牵制
- **缺点**：见"背景"。树莓派端要维护两套解析器，CRC 实现必然漂移

**→ 否决。**

## 后果

### 正面

- 树莓派端只需要一个帧解析器，命令表按 `board_type` 分派
- `crc16.c` / `protocol_frame.c` 在 `src/firmware/common/` 只存一份，
  task-10 与 task-11 通过 `-I../common` 共享，不存在"改了一边忘了另一边"
- 换 MCU 时只需重写 HAL 层（`encoder.c` / `motor.c` / `uart.c`），
  帧层与命令表原样搬过去
- 帧格式被单元测试锁定（黄金帧字节序列 + CRC 标准向量 + 0~251 全长度往返 +
  逐比特错误注入），任何人"顺手优化"协议都会立刻收到红灯

### 负面

- 二进制协议不能用串口助手直接读，调试依赖解析脚本
- 不做转义带来的失同步窗口（见决策 3），需要物理层配合做空闲重同步
- LEN 包含 CRC/EOF 的语义不直观，新人容易算错——只能靠文档和测试兜住

### 风险

- **三方实现漂移**：C 固件 ×2 与 Python 上位机 ×1，共三份实现。
  缓解：三方都必须通过 `crc16("123456789") == 0x29B1` 与本文档的黄金帧字节序列；
  task-15 的集成验证脚本会做跨端往返测试。
- **DATA 长度上限 251 字节**：当前最长载荷是 TELEMETRY 的 34 字节，余量充足。
  若将来要传图像等大块数据，本协议不适用，应另开一条链路而不是扩展本协议。
