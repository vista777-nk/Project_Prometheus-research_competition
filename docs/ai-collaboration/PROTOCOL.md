# 双 AI 协作协议（DeepSeek × Claude）

> **版本**：v0.1（草案，§10 各项待负责人确认） · **日期**：2026-11-06
> 本协议细化 [AI_OWNERSHIP_HANDOFF.md](../AI_OWNERSHIP_HANDOFF.md) §8。两者冲突时以交接书为准；与 ADR 冲突时以 ADR 为准。

## 1. 原则

1. 仓库是唯一事实源。聊天记录不算证据；代码、ADR、实验记录、日记、[CLAIMS.md](./CLAIMS.md) 才算。
2. 两个 AI 对等，不预设分工。谁在 CLAIMS.md 登记，谁负责该事项。
3. 分支即锁：同一时间一条分支只有一个写者。
4. 不替对方「修好算了」：发现问题先写现象和证据，再改。
5. 不确定的事找负责人，不靠猜。见 §9。

## 2. 认领与分支锁

1. 动手前先在 CLAIMS.md 登记：事项、认领者（DeepSeek / Claude）、分支、基线 SHA、状态。登记行和第一批改动在同一条分支上提交，这样登记随分支一起被对方看到。
2. 分支从集成分支切出（当前为 `dev`，见 §10 待确认项），命名按 CONVENTIONS.md §1.1：`feat/`、`fix/`、`docs/`、`exp/` + 英文描述。不直接在 `dev` 上提交。
3. 认领超过 7 天没有新提交，视为过期。对方不得直接接管分支：先在 CLAIMS.md 备注并通知负责人；确需继续时，从原分支 HEAD 切新分支并登记。
4. 两条分支要改同一文件时，先在 CLAIMS.md 备注。后合并的一方负责 rebase 与解决冲突，不得覆盖对方已合并的结果。
5. 单写者资源，不要并发修改：
   - 同一份 `docs/decisions/ADR-*.md`；领 ADR 编号时先在 CLAIMS.md 登记编号，避免撞号。
   - CLAIMS.md 中不属于自己的行。
   - `Research_Diary.md` 只在末尾追加带日期的小节，不改旧内容。

## 3. 状态

CLAIMS.md 的状态只用下列几种：

| 状态 | 含义 |
|------|------|
| 未认领 | 可以领 |
| 进行中 | 有分支，认领者在写 |
| 待审查 | 已推送，等对方或负责人审查 |
| 待负责人 | 需要硬件、经费、发布或治理决策 |
| 阻塞 | 等外部条件，备注写清等什么 |
| 完成 | 满足 §5，且已合入集成分支 |

## 4. 交接

不转述聊天。交给对方三样东西，写在 CLAIMS.md 对应行的备注和 `Research_Diary.md` 当天小节里：

1. 分支名 + commit SHA；
2. 改动文件清单与未完成项；
3. 复现命令与实测结果，包括失败尝试。

会话结束时同时更新日记（发现 / 完成 / 失败 / 小结 / 下一步）；状态或阻塞变化时更新交接书 §2 与 §6。

## 5. 完成定义

声称「完成」之前，必须在本次改动上实际跑过并记录结果：

1. `git diff --check`
2. `make smoke-phase1`
3. `bash src/deployment/validate.sh`（本机缺依赖时会 SKIP，要如实写出）
4. 受影响模块的 Host 测试（STM32 / MSPM0 / 传感器）；涉及 ROS 的改动需要在 Ubuntu 服务器上跑 `make test-all`
5. 推送后确认当前分支的 GitHub CI 实际出现并全绿；无法确认就写「CI 状态未验证」
6. 汇报时分开写「验证了什么」和「没有验证什么」，数字用实测值，注明环境

文档类改动至少做第 1 项，并核对改动涉及的链接和数字有出处。

## 6. 交叉审查

1. 进入集成分支前，由另一个 AI 或负责人审查。审查者只看 diff 和测试输出，不先看作者的结论，以免被锚定。
2. 审查意见写进 PR 描述或 CLAIMS.md 备注，写现象和证据，不写「我觉得不对」。
3. 作者逐条回应：改了、不改（写理由）、或升级给负责人。
4. 谁来点合并按钮：**待负责人确认**。在确认之前，AI 不自行合并到集成分支。

## 7. 分歧处理

两个 AI 意见不一致时，不来回回滚。各写一段：立场、证据、选择它的代价，放进 ADR 草案（状态 Proposed）或 CLAIMS.md 备注，交负责人决定。优先级：ADR > 交接书 > 本协议 > 任务文档 > 口头约定。

## 8. 提交与推送

1. Conventional Commits + 简体中文；正文写改了什么、实测数字、仍未验证项。
2. 保留各自工具自动加的 Co-Authored-By 脚注，用它区分是谁写的；不手写别的归属行。
3. 不 force-push 共享分支，不跳过钩子，不改写已推送的历史。
4. 不提交密钥、`.env`、序列号、MAC、校园网临时 IP；不提交 build/devel/install 与固件编译产物。

## 9. 必须升级给负责人的事项

- 任何硬件接线、上电、拆装桨、飞行、动力台测试
- 修改既有 ADR 结论，或改变门禁强度（阻塞 ↔ 告警）
- 改分支模型、打 tag、发版
- 对外投稿、竞赛报名、经费与采购
- 开启 Phase 2 实机工作，或重排 ROADMAP 时间线
- 暴露任何网络端口，或批准跨校区隧道
